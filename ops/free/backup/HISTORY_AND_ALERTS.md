# Dated history and owner alerts

The existing UTC hourly:20 checkpoint still writes its current game/membership pair in one PostgreSQL transaction after obtaining both existing try-locks. Its first successful checkpoint of each UTC day additionally anchors the complete pair in `nrn_backup_history`. Later checkpoints on that date update only the current pair; they neither duplicate nor retransmit the dated payload. Retention keeps at most14 UTC dates and64MiB of measured JSONB text payload, pruning oldest anchors in the same transaction. A reversed clock or oversized capture preserves existing dated copies. Provider storage/index overhead is additional; current small snapshots remain far below the existing free allocation. No new resource or tier is provisioned.

The checkpoint writes metadata only to `/var/lib/nrnplay-backup/status.json`. Successful timestamps are recorded only after commit. Failures and writer skips retain the previous successful timestamp. Node-free pressure skips naturally make the last success older. The status folder is0750 nrn:nrn-backup, status file0640, and contains only a timestamp/outcome. Primary snapshots remain0700/0600 and are not shared with the alert account.

The hourly:35 watcher reads this local metadata and never opens PostgreSQL or keeps Neon awake. It reports a copy stale after3hours, gives missing initial metadata a3hour bootstrap grace, attempts one stale notice per incident with at most one reminder per24hours, then one recovery notice when a newer successful copy exists. An email attempt is persisted before sending, so uncertain sends/crashes are not immediately retried. Transport failures are logged only as fixed metadata, with no recipient/token/provider response. No test email is sent during deployment while backups are fresh.

Deploy requires a dedicated nologin `nrn-alert` user and `nrn-backup` group. The checkpoint runs as existing uid nrn with primary group nrn-backup; the notifier uses uid nrn-alert with that group and can read only the aggregate status. Its own attempt state is0700/0600. Systemd loads a separate root0600 `/etc/nrnplay/backup-alert.env` before isolating the process: private `NRN_BACKUP_ALERT_EMAILS` derives only from the already-approved normalized owner allowlist, plus only the active existing email provider credentials. Never include DATABASE_URL, MEMBERSHIP_AUTH_SECRET, payment/admin keys or snapshot paths in the notifier environment. Do not place any address/key into Git.

Both jobs keep pre-Node pressure checks and RACE priority. The watcher has CPUWeight5/Nice19/OOM900, MemoryHigh48M/Max96M/Swap32M and60seconds maximum. It is intentionally skipped under RACE pressure. The backup retains its existing CPU10/Nice10/OOM800 and128M/192M/128M memory limits. No app/runner restart is required merely to change these oneshot units; the new compiled code must already be selected by current before installing/enabling them.

Before enabling the watcher: manually run the actual checkpoint once with its production unit; confirm status=written, local successful timestamp, a single current UTC anchor and retention metadata. Run watcher `--plan` with the separate private environment to confirm fresh/no notice/two configured owners, then run the real unit (fresh means no email). Validate one dated pair via `readPostgresHistoryPair(client, 'YYYY-MM-DD', fixtureSecret)` in a bounded read-only connection and the independent offline restore verifier. The public fixture secret is only for schema loading; do not authenticate real users or move the principal key. This reader validates the date, selects one bounded pair without advisory locks/DDL/writes, and uses a READ ONLY transaction. It must not install files under the primary directory.

Keep rollback material private. Reverting these unit templates to the prior ones stops history/status generation but leaves current snapshots and existing history untouched. Disable the new alert timer before reverting its code. Never delete a verified backup to force a restore or a startup. Every actual restore uses a separate private target and requires a coordinated writer cutover for production; source-only rollback after a live v4 opt-in cannot use the old v3 parser.
